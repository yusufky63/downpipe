# Security model

A download manager handles untrusted data from servers and, through the browser extension, from web pages. This page lists what Downpipe trusts, what it does not, and how each boundary is enforced today.

## Untrusted inputs and how they are handled

| Input | Risk | Handling |
|---|---|---|
| `Content-Disposition` and URL file names | Path traversal (`../`), absolute paths, Windows device names (`CON`, `COM1`), reserved characters, hidden extensions via trailing dots | `filename::sanitize`: keeps only the last path component, replaces `<>:"/\|?*` and control characters, strips trailing dots and spaces, prefixes device names, caps length at 200 bytes while keeping the extension. Existing files are never overwritten. |
| Range responses | A server that ignores ranges or changes the file mid-download produces a corrupt file | Every follow-up `206` must match the first offset, total size and ETag; a `200` to a range request is rejected; changes restart the download from zero. |
| Server-sent bytes beyond the announced size | Writing past the end | Writes are clipped to the segment and the announced size. |
| `Retry-After` | A huge value parks a download forever | Capped at 10 minutes. |
| Redirects | Loops | At most 10 redirects. Follow-up requests use the final URL of the current session; resumes go through the original URL again because redirect targets often expire. |
| TLS | Interception | Certificate validation is always on (rustls with the platform verifier). There is no option to turn it off. |
| Messages from the browser extension | A compromised or buggy extension, or any local program that opens the pipe, sending crafted requests | Fixed, versioned schema checked by both the native host and the app (see [Browser bridge](#browser-bridge)). |
| Stream manifests (HLS, DASH) | Huge or malicious manifests, entity expansion, URLs to local files, endless segment lists, protected media | At most 8 MiB per manifest; XML is parsed without a DTD, so no entities are expanded; every URL must be http(s); at most 100,000 segments per track; arithmetic on manifest values is checked. DRM and live streams are refused while parsing, before any media request (see [Streams](#streams)). |
| Page and frame data in the extension | A page influencing what the extension sends | The service worker classifies requests from response headers the browser reports; the overlay button's requests name no tab (the browser says which tab sent them) and are validated like the popup's. |
| yt-dlp's output (`-J` JSON, progress lines, error messages) | A broken or replaced yt-dlp, or a page whose metadata is crafted, feeding the app bad data | `-J` output over 64 MiB is refused; only the fields Downpipe uses are read, with their types checked; titles lose control characters and are capped at 200 characters; format ids are kept only as plain tokens (letters, digits, `-`, `_`, `.`), because they go back into a format selector. Progress is read only from lines that start with Downpipe's own markers, as JSON. Error texts are capped at 300 characters. See [Site providers](#site-providers-yt-dlp). |
| yt-dlp and Deno downloaded by the app | A tampered or corrupted program | Only on the user's request, only from the projects' own GitHub releases, and only after the SHA-256 the release publishes matches; see [Site providers](#site-providers-yt-dlp). |
| Archives extracted after download (zip, tar, 7z) | Zip slip (`../`), absolute and drive paths, links that point outside the folder, zip bombs, crafted XZ headers | Every entry becomes a path of sanitized components inside a new folder; unsafe names, links and special files are left out; files are created with `create_new`; the bytes written are counted against a budget. See [After a download](#after-a-download). |
| File names and URLs in post-download commands | Shell injection (`; rm -rf ~`, `$(...)`, `&`), argument splitting | The command line is split by Downpipe before placeholders are filled in, and the program runs from an argument array, never a shell. See [After a download](#after-a-download). |
| Backup files and IDM lists | A crafted backup or export, from another person or another machine, adding `file:` links, writing over files, pointing tool paths or post-download commands at another program, or carrying cookies | Read in Rust, never by the web view, with size limits (64 MB backups, 32 MB IDM lists). Each download is checked on its own (http/https links only, sanitized names, absolute paths only, unfinished downloads added paused) and imports only add catalog rows, so no file is written; the engine saves a resumed download under a free name. The FFmpeg, yt-dlp and Deno paths, the post-download and per-queue command lines, the scanner command and the remote control settings are never imported (a backup does not even carry the token's hash), and an imported feed only remembers what it holds instead of downloading it. From IDM's lists only links and file names are read (and on Windows six named registry values, with `KEY_READ`); cookies, headers and credentials are skipped. See [BACKUP_AND_IMPORT.md](BACKUP_AND_IMPORT.md). |

## Secrets

- `user:password@host` in a URL is used for HTTP Basic auth by the HTTP client, but URLs are stored with credentials removed (`redact_url`). Logs use `display_url`, which also drops the query string, because signed URLs carry tokens there.
- Custom request headers (for example `Referer`) are kept in memory only and never written to the meta file or the database. After a restart such downloads continue without them.
- Error messages shown in the UI are built from error classes, not from the HTTP client's display string, which can contain the full URL.
- Downpipe does not read browser cookies, and the bridge refuses any message that tries to carry them. The only cookies it ever sends are ones the user types or pastes into the desktop app's Add dialog (the **Request headers** field or a **Paste as cURL** command); like every custom header they stay in memory and are never written to disk or logged. A future opt-in, per-site cookie feature is described in the roadmap and will never log or store cookie values.

## Desktop app

- The web view runs local, bundled content under a strict CSP (`script-src 'self'`, no remote origins).
- It holds only Tauri's `core:default` capability, and so does the confirmation window's web view; neither can show, move or close a window itself. Folder pickers and "open" / "show in folder" run in Rust, and those commands take a download id, not a path, so a compromised web view still cannot open arbitrary files.
- No network port is opened, including for the browser bridge, unless the user switches on the remote control (see [Remote control](#remote-control)).
- Dragging a finished file out of the list (`start_drag`), like opening or revealing it, takes a download id; the path comes from the catalog.
- **When done** runs fixed commands with argument arrays (`rundll32 powrprof.dll,SetSuspendState`, `shutdown /s /t 0` from `System32` by absolute path; `pmset`/`osascript` on macOS; `systemctl` on Linux). Nothing from the web view or a server reaches them, and they run only after a visible 60-second countdown with Cancel. The only programs the user can have run are the post-download command and the virus scanner they type in (see [After a download](#after-a-download)).
- **Open folder** for an extracted archive takes a download id; the folder comes from the catalog, like the other file actions.
- The sign-in item is created only when the user turns on **Start Downpipe when you sign in**, and removed when it is turned off.
- **Save list** writes the stored URLs, which never contain `user:password@` credentials; headers are not exported.
- **Offer to download copied links** is off by default. While it is on, the app reads the clipboard's text (on Windows only after the clipboard's change counter moved), keeps the last text in memory to notice changes, and does nothing with it unless it is a single http(s) link to a listed file type. That link is only put into the Add dialog; nothing is downloaded until the user confirms, and nothing is written to disk or sent anywhere. What was on the clipboard when watching started is never offered.
- The web view's own context menu and the browser keys (reload, print, save, view source, find, history, back and forward) are cancelled, and so are the developer tools keys in release builds, so the window cannot be navigated away from the bundled UI by a stray key.
- **Download again** with **Replace the existing file** deletes the old file before downloading; the dialog says so and the box is off by default. Without it the old file is never touched.
- **Ask before downloads from the browser start** (on by default) keeps a download sent through the bridge paused until the user picks its name and folder in the app. Any program running as the same user can reach the pipe; with the setting on, such a program cannot start a download through it unnoticed either.

## Integrity

- Data reaches its final name only through an atomic rename after the last byte is written and, if requested, the checksum matches.
- Resume metadata is written with write-to-temp-then-rename after the data it describes has been synced.

## Browser bridge

The path is extension, then Native Messaging to `downpipe-native-host`, then a local pipe to the app. Details in [BROWSER_BRIDGE.md](BROWSER_BRIDGE.md).

**Who may start the host.** Browsers start a Native Messaging host only for extensions its manifest lists, and they do not accept wildcards. `install`, and the desktop app at start-up, write the Downpipe extension's id explicitly (`allowed_origins` for Chrome, Edge and Chromium, `allowed_extensions` for Firefox). The Chrome manifest carries a public key so that unpacked builds get that same id. Registration is per user (`HKEY_CURRENT_USER`, or files in the user's home), so no administrator rights are involved. The app only ever points the registration at the host next to its own executable and keeps, but never adds, other extension ids; it does not read or write `HKEY_LOCAL_MACHINE` or system-wide manifest folders.

**Video pages.** On a YouTube video page the extension sends the page's address and the tab's title as a `page` message, never the media requests the page made and never cookies. The popup reads the address with the `activeTab` grant it gets when opened; the overlay's third request (`overlay_page`) names no page, and the service worker takes the page from the sender's own tab (or the frame of an embedded player) as the browser reports it. Only addresses `lib/sites.ts` recognizes are sent, rewritten to `https://www.youtube.com/watch?v=<id>`; the app checks them again against the same rules and answers `unsupported_page` otherwise. The context menu item **Download this video with Downpipe** is limited to those pages by its document patterns.

**Extension permissions.** `activeTab`, `contextMenus`, `nativeMessaging`, `notifications`, `scripting` and `storage`; `downloads` only while download capture is switched on; and `webRequest` with access to `http://*/*` and `https://*/*` only while media detection is switched on (the access to the sites may also be granted from the options page for Alt+click, below). All three are optional permissions the popup requests and removes with its switches. No `<all_urls>`, no content scripts in the manifest, no web-accessible resources. The extension never reads cookies, and its one network request of its own, reading HLS playlists during media detection, sends none.

**Media detection.** While it is on, the service worker observes media, XHR and fetch requests (and page loads, to clear a tab's list); it does not block, change or read the body of any request. Of the request headers it keeps only `Referer` and `Origin`, in memory and by request id until the response starts (at most 500 at a time); in Chrome reading them needs the `extraHeaders` option, which costs the browser a little speed on those requests while detection is on. Cookies and authorization headers are never read or kept. It keeps, per tab and in session storage only, at most 20 media addresses with their type, size and the address of the frame that requested them, and forgets a tab's list when the tab loads another page or closes, and all lists when detection is turned off.

**Reading playlists.** To offer a stream once instead of once per quality, the service worker fetches each HLS playlist (`.m3u8`) a tab loads, once, if it is not already listed or known: a request of its own to the same address, which the access to all sites granted for detection allows. The request carries no cookies (`credentials: "omit"`), no referrer and no headers from the page, so a playlist that needs the page's session simply fails and is listed as before. It reads at most 256 KiB and 5 seconds per playlist, stops at the first segment of a media playlist, and reads at most 4 playlists at once, with up to 40 more waiting their turn (beyond that a playlist is listed unread). Of the text it keeps only whether it is a master playlist, the number of video qualities and the addresses on its `#EXT-X-STREAM-INF`, `#EXT-X-MEDIA` and `#EXT-X-I-FRAME-STREAM-INF` lines, resolved against it; addresses that are not http(s) or are over 8 KiB are dropped. Those addresses (at most 400 per tab, in session storage, forgotten with the tab's list) only decide what is not listed. The extension's own request has no tab, so detection does not see it, and nothing from it is sent anywhere. DASH manifests are not read. Nothing is sent to Downpipe until the user presses a Download button; then the stream's address, the page address, the referrer and origin the player sent, and the page title go to the local app, never cookies or other headers. Sites on the excluded sites list are left out of detection, and the overlay script is registered with them as exclude patterns. The overlay button is a content script registered with `scripting.registerContentScripts` only while detection is on. It lives in a closed shadow root, so the page cannot read or restyle it, and it ignores events that are not `isTrusted`, so page scripts cannot click it. It may send three requests, list, send and (on a video page) send the page, and all act on the sender's own tab as the browser reports it (`sender.tab.id`); the list request may carry the video's own source and poster addresses, checked as http(s), which only narrow the tab's list down to that video's entries and are not stored or sent to the app; the service worker accepts them only from this extension's content script in an http(s) page and refuses every popup request from there. Media from a page is untrusted: addresses are checked as http(s) and length-capped, stored entries are validated again when read, and texts are written with `textContent`. Pages can detect that the button exists once it is shown; that is the price of the feature, and it is off by default.

**Alt+click.** The script that lets the browser download a link clicked with Alt (or Shift) is registered only while capture is on, the key is not off and the access to the sites is granted. It has no user interface and reads only the key from the extension's settings. It acts only on `isTrusted` clicks, so page scripts cannot trigger it, and its one request names an http(s) address, which the service worker checks again (exact shape, http(s) only, from this extension's content script in an http(s) page) before the browser downloads it. The download is the browser's own; nothing goes to Downpipe.

**Reading a page's links.** `activeTab` and `scripting` exist for **Download links on this page**. `activeTab` gives access to one tab only after the user clicks the extension's context menu item or opens its popup there, and only until that tab navigates; without such a click the extension cannot read any page. The injected function runs once in the page's isolated world and only returns the page address, its title and its http(s) links with their visible text, capped at 2,000 links. It sends no messages, so the service worker's sender check is unchanged. The page's DOM is untrusted: the service worker validates the result again (http(s) only, length caps, control characters removed) before storing it in `storage.session`, which content scripts cannot read, and the links page validates it once more when it reads and removes it. The popup also uses the `activeTab` grant to read the current tab's address for **Pause capture on this site**.

**Inside the extension.** The service worker answers messages whose sender is this extension's own pages (the popup, the capture filters page and the links page): the sender id must match and its URL and origin must be the extension's base URL. The only other sender it answers is its own overlay script in a web page, with the three requests described under media detection. Each message kind has an exact shape, and anything else (an unknown kind, an extra field, a non-http(s) link, a site or file type list that is not in its normalized form) is refused. It registers no `onMessageExternal` listener, so other extensions and web pages cannot drive it. Strings from the host and link texts from pages are length-capped and written with `textContent`, never as HTML.

**Messages.** Requests have a fixed, versioned schema (`protocol_version: 1`). A `media` request carries a manifest URL, `hls` or `dash`, a page URL, a referrer, an origin (exactly `scheme://host[:port]`) and a title (at most 200 characters, no control characters) under the same rules. A `page` request carries only a page URL, which must be a recognized video page, and a title. The host rejects unknown or duplicate fields, any field whose name mentions cookies, non-http(s) URLs (`javascript:`, `file:`, `data:`, `blob:` and so on), control characters (which URL parsers would silently drop), URLs over 8 KiB, file name hints with folders, and frames over 64 KiB, before allocating the frame. Referrers and page URLs lose credentials and fragments; the referrer the extension computes follows the browser's default `strict-origin-when-cross-origin` policy, so a cross-site link gets only the page's origin.

**The pipe.** On Windows the app creates `\\.\pipe\downpipe-bridge-<user>` as the first instance (so it fails rather than joins a pipe someone else created), refuses remote clients, and keeps the default security descriptor: write access only for the user, SYSTEM and administrators, and a medium integrity label that keeps sandboxed, low-integrity processes such as browser renderers out. The host opens the pipe with `SECURITY_IDENTIFICATION`, so even a process that squatted the name could not impersonate the user. On macOS and Linux the socket lives in a folder created with mode `0700` (the app refuses a folder others can enter) and the socket itself is `0600`.

**Starting the app.** When a `download`, `media` or `page` message finds the app closed (and the extension did not send `start_app: false`), the host starts the app, but only an executable in its own folder under one of a few fixed names (`Downpipe.exe`, `downpipe.exe`, `downpipe-desktop.exe`, without `.exe` elsewhere) and only with `--hidden`. Nothing in the message chooses the program or its arguments, and the app's standard streams are not connected to the host's, so it cannot write into the protocol. `ping` and `tasks` never start it.

**The app trusts nothing on the pipe.** Any program running as the same user can connect, so the app validates every request again with the same code, accepts one request per connection, drops idle connections after five seconds, and only ever calls `Manager::add`. A request cannot choose the download folder, pass headers other than the referrer (and, for a stream, the origin), or touch existing downloads. A `page` request passes no headers at all. Before the user answers the confirmation dialog of a stream, the app fetches only its manifest, to list the qualities; for a video page, yt-dlp fetches only the page and its player data (`-J`). Progress queries (`tasks`) take at most 20 ids and answer only for those ids, so the extension cannot list the user's other downloads.

**Privacy.** The app stores the download URL (without credentials) as it does for any download; the page URL is not stored. Private-window downloads are never captured. The popup's activity list and collected page links are kept in session storage and cleared when the browser closes; collected links are also removed once the links page has read them (that tab keeps its own copy in its `sessionStorage`, so a reload still works, until the tab closes). The capture filters (file types, excluded sites, minimum size) stay in the extension's local storage and are never sent anywhere.

**Known limits.** A process running as the same user can add downloads through the pipe, the same as it could by driving the app's window. On Windows another account could claim the pipe name before Downpipe starts; it would then receive the URLs the host sends, though not the user's credentials or token. Both are within the "same user / same machine" trust boundary this model assumes.

## After a download

Once a download completes, Downpipe can scan it, extract it and run a command, in that order (`crates/core/src/post/`). Each is off until the user turns it on.

**Only what the user typed runs.** The command comes from **Settings → After download**, a queue's command, or the download's own field in the Add, confirmation and details dialogs, all typed by the user in the app. Nothing a server, a web page, the browser extension or a remote-control client sends can set it: the bridge's messages and the remote API's requests have no such field, the site grabber and feeds add downloads without one, and `AddOptions::post` is filled only by the app's own dialogs. A download added through those ways still gets the user's own default or queue command, with its name and URL only as arguments. The scanner is Microsoft Defender at `%ProgramFiles%\Windows Defender\MpCmdRun.exe` or the command the user sets. A command line that cannot run safely is refused when it is saved, not when a download completes.

**No shell.** The command line is split into words once, by Downpipe's rules (spaces separate, `"..."` and `'...'` group, backslashes are ordinary characters), and only then are `{path}`, `{name}`, `{folder}` and `{url}` filled in, inside each word. A value is inserted as it is and never read again, so a file named `a"; rm -rf ~; ".zip` or a URL with `&` and `$(...)` stays one argument. The program starts from that argument array (`tokio::process::Command`), never through `cmd /c`, `sh -c` or PowerShell. On Windows, Rust quotes each argument for the program's own parser, and refuses arguments it cannot quote safely for `.bat` and `.cmd` files.

- The program must be a bare name, looked up on `PATH`, or an absolute path; a relative path such as `tools\run.exe` is refused, because it would be resolved against a folder the user does not see. The program word cannot be a placeholder.
- It runs in Downpipe's own working folder, never the download folder, so the program does not pick up a DLL or script a download put there. stdin is closed and no console window opens.
- `{url}` is the stored URL, with `user:password@` already removed, so credentials do not show up in a process list. `{path}` and `{folder}` are absolute. `{name}` is the sanitized file name; a name can start with `-`, so prefer `{path}` where a program might read it as an option.
- Runs end after the time limit (10 minutes by default, 5 seconds to a day): on Windows the program is in a job object that ends everything it started, on macOS and Linux it leads its own process group, which is killed. They also end when the download is removed or downloaded again, and when Downpipe quits; post-download steps do not resume after a restart.
- Only the last 4 KiB of stdout and stderr are kept, without control characters, in the log and the download's report.
- Nothing runs for a download that failed, was paused or was canceled.

**Virus scan.** Off by default. Defender runs as `MpCmdRun.exe -Scan -ScanType 3 -File <path> -DisableRemediation`: exit code 0 is clean, 2 a threat, anything else an error. `-DisableRemediation` keeps Defender from quarantining or deleting the file; Downpipe does not delete it either. A threat found marks the download, shows a notification whatever the finish notifications are set to, and stops the rest: the archive is not extracted and the command does not run. A custom scanner gets the file as `{path}` or as its last argument and follows ClamAV's exit codes (0 clean, 1 a threat). A missing scanner is reported as such, not as clean. Real-time protection may of course act on the file before Downpipe's scan does.

**Extracting archives.** Off by default; switched on per category or per download. Zip (Stored, Deflate, Deflate64, LZMA, XZ), tar, tar.gz, tar.xz and 7z (LZMA, LZMA2, BCJ filters) are read by pure-Rust crates (`zip`, `tar`, `flate2` on `zlib-rs`, `lzma-rust2`, `sevenz-rust2`), in the app's process, without running any program. RAR is not supported: no permissively licensed Rust implementation exists, and unRAR's license does not allow it; 7-Zip run as the post-download command can extract it. Encrypted archives are refused.

- The files go into a new folder next to the archive (`a.zip` -> `a`, `a (1)` when that exists), created with `create_dir`, so the extraction owns all of it.
- Each entry name is split on `/` and `\`; a name with `..`, starting with `/` or `\` (absolute, UNC, `\\?\`), or with a drive (`C:`) is left out, `.` and empty components are dropped, and every component is sanitized like a server-supplied file name (reserved characters and `:` (alternate data streams) replaced, Windows device names prefixed). Nothing can be written outside the folder.
- Symbolic and hard links, devices, FIFOs and other special entries are left out, so no link exists in the folder for a later entry to follow. Files are opened with `create_new`: a second entry with the same name is left out rather than overwriting the first. Only the executable bit of Unix modes is kept (`0755`), never setuid or other bits, and no extended attributes are written.
- **Zip bombs.** The bytes actually written count, not the sizes in the headers: an archive may expand to at most 200 times its own size (at least 256 MiB, at most 64 GiB) and have at most 100,000 entries. A declared size beyond what is left stops it early. Entries skipped in a solid 7z block are decompressed into nothing but still counted. XZ streams may ask for at most 512 MiB of dictionary. Archives inside the archive are not opened.
- Any error, a limit reached, or a removal of the download deletes the partial folder, which is Downpipe's own. The entries left out are counted in the report.
- **Delete the archive after extracting it** (off by default) deletes it only when every entry was extracted, and only after the command ran.

## Streams

- **DRM.** HLS keys with a method other than `NONE` or `AES-128`, or any key format other than `identity` (FairPlay, Widevine, PlayReady), and DASH manifests with `ContentProtection` anywhere fail the download with `drm_protected` while the manifest is parsed, before any segment, init section or key is requested. AES-128 is decrypted because its key is an ordinary file any player receives; it is kept in memory only.
- **Live streams** fail with `live_stream`: they would never end.
- **Work folder.** Fragments are written only inside `<name>.part/` next to the final file, under names Downpipe makes (`t0-000042.frag`), never under names from the manifest. Removing a stream download deletes that folder only if Downpipe's `media.json` is in it.
- **FFmpeg** is not shipped. Downpipe looks for it in the path set under **Settings → Media**, else on `PATH` (absolute folders only), and starts it with an argument array, never a shell, with no console window, stdin closed and its stderr read for the error message. It only reads track files Downpipe joined and writes one file in the work folder; it is stopped if the download is paused. A path the user enters runs as that program, like any tool chosen in a settings page.

## Site providers (yt-dlp)

Video pages (YouTube) are downloaded by [yt-dlp](https://github.com/yt-dlp/yt-dlp), an external program, run by `crates/providers`.

- **Process.** yt-dlp starts from an argument array, never a shell string, with no console window and stdin closed. Every run passes `--ignore-config` (a yt-dlp configuration file on the machine cannot add options such as cookies, an output folder or a playlist), `--no-cookies`, `--no-cookies-from-browser` and `--no-playlist`, and the page URL comes last, after `--`, so it can never be read as an option. Downloads add `--match-filters "!is_live & live_status != is_upcoming"` and `--max-downloads 1`. yt-dlp gets the proxy from the settings and nothing from the browser.
- **What reaches yt-dlp from outside.** The page URL, which is a recognized video page in its canonical form; the format ids the user picked, which must be plain tokens and are combined by Downpipe into the selector (a value with `+`, `/` or `[` is dropped and the best quality is taken instead); the file name stem, which is sanitized like any server-supplied name, with `%` doubled for yt-dlp's output template; and the download folder of the record, passed with `-P`.
- **Stopping.** Pausing or cancelling ends yt-dlp and everything it started: on Windows the process is put in a job object that kills its processes when terminated or closed (so they also end if Downpipe exits), on macOS and Linux it leads its own process group, which is killed. A pause leaves yt-dlp's `.part` files for `--continue`; a cancel or a removal with files deletes only the files named `<stem>.f<id>.<ext>`, `<stem>.<ext>.part`, `.part-Frag<n>`, `.ytdl` and `<stem>.temp.<ext>` next to the download, never a finished file and never another name.
- **Name collisions.** Before the first start Downpipe picks the stem; if a finished file already has it, `<stem> (1)` and so on, so yt-dlp never mistakes an earlier download for this one and never overwrites it.
- **DRM and live.** `-J` output with `_has_drm`, or with only protected formats, fails with `drm_protected`; protected formats next to free ones are left out of the list; live and upcoming videos fail with `live_stream`; yt-dlp's own DRM errors map to `drm_protected` as well. Nothing is downloaded in either case.
- **JavaScript runtime.** yt-dlp runs parts of YouTube's player code in Deno (or Node) to answer its challenges; that code comes from YouTube. Downpipe passes the runtime's path with `--js-runtimes` and nothing else. It does not pass `--remote-components`, so yt-dlp does not fetch extra scripts from the network; the official yt-dlp builds include their challenge solver.
- **Downloading the tools.** Nothing is downloaded until the user presses the button in **Settings → Media**. It then resolves the latest release of `yt-dlp/yt-dlp` and `denoland/deno` on github.com, downloads the official build for this system (at most 400 MiB) next to the tools folder under a temporary name, and compares its SHA-256 with the one the release publishes (`SHA2-256SUMS`, or Deno's `<file>.sha256sum`). Only a match is moved into place, by rename; a mismatch, a missing hash or a failed download leaves the previous copy untouched and deletes the temporary file. Deno's zip is read for its one program. The hash comes from the same release, so it protects against corrupted and altered transfers, not against a compromised release; users who want to check signatures (yt-dlp signs `SHA2-256SUMS`) can install the tools themselves and set their paths. Nothing updates on its own.
- **Paths from the settings** run as those programs, like FFmpeg's.

## Remote control

**Settings → Remote** can serve a small HTTP API and a web page (`crates/remote`, `downpipe-remote`) so a phone or another browser can see the list, add links and pause, resume or remove downloads. Download managers have shipped this badly before: [AB Download Manager #1401](https://github.com/amir1376/ab-download-manager/issues/1401) listened on the network with no authentication, so anyone on the same Wi-Fi could add downloads. Downpipe's version is built around that lesson.

| Threat | What an attacker could do | Mitigation |
|---|---|---|
| Someone on the same network (café Wi-Fi, a shared flat, an infected device on the LAN) | Find the port and drive the API | Off by default. Listens on `127.0.0.1` unless the user explicitly picks a network address, with a warning that the token is then the only barrier. Every API request needs the token; nothing but the page's static files answers without it. |
| Guessing the token | Brute force | 160 random bits from the operating system's generator (`getrandom`), 32 base32 characters. After 10 wrong tokens within 10 minutes a peer (an IPv4 address, or an IPv6 /64) gets `429` for the rest of that window without its token being checked, so further guesses learn nothing; at most 4,096 peers are tracked. Tokens are compared as SHA-256 hashes in constant time. |
| Token theft from the computer | Reading the token from Downpipe's files or settings | Only the token's SHA-256 is stored (in the catalog's settings); the token is shown once when it is made and never again. **New token** replaces it and the old one stops working at once. |
| Token theft in transit | Reading it off the network, from logs or from referrers | The API is plain HTTP on a local network, so someone who can watch that network's traffic could read the token; that is why the network choice carries a warning, and why **New token** exists. The link and QR code carry the token in the URL fragment (`#token=`), which browsers never send to a server or put in a `Referer`; the page moves it into its own storage and removes it from the address bar at once. Requests carry it only in the `Authorization: Bearer` header, never in a URL, and the page sends `Referrer-Policy: no-referrer`. Neither tokens nor links are logged. |
| A page on another site in the user's browser (CSRF, DNS rebinding) | Making the browser call the API | No CORS headers are sent, preflights are refused, and a request whose `Origin` is not the server itself (or whose `Sec-Fetch-Site` is `cross-site`) gets `403`. A rebinding page reaches the server under another name but has no token, which lives in the real origin's storage. The page has a strict CSP (`script-src 'self'`, `connect-src 'self'`, `frame-ancestors 'none'`) and `X-Frame-Options: DENY`. |
| The internet | Reaching a forwarded port or a computer with a public address | A network-facing listener answers only loopback, private (RFC 1918, IPv6 unique local), link-local and shared (`100.64.0.0/10`, used by Tailscale and similar) addresses, and refuses everything else with `403`. |
| Oversized or flooding requests | Exhausting memory or threads | Request bodies are capped at 16 KiB and links at 8 KiB; at most 32 requests are handled at once, the rest get `503`. |
| A stolen token in use | Damage through the API | The API can only list downloads (name, size, state and the link's host, never folders, paths or full links, whose query often carries a signature), add http(s) links, pause, resume and remove downloads, and read harmless settings (queues, limits, language; no folders, proxy, tool paths or anything about the remote control). The folder of a new download is a name inside the download folder (`Movies/2026`); absolute paths, drive letters, `..` and names the file system would change are refused. Removing a finished download never deletes its file; removing an unfinished one deletes only what it wrote. There is no file browsing, no opening of files and no command. |

**Known limits.** The connection is not encrypted: it is HTTP on the local network, and a self-signed certificate would only teach users to click through warnings. Anyone holding the token can add downloads, which then fetch from the internet on the computer, and a download can be large. The firewall question Windows may ask when a network address is chosen comes from the system, not from Downpipe.
